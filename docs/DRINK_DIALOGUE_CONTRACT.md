# Напитки и паузы в диалоге

Статус: реализованный контракт редактора и игры. Предметный пример — Вера ищет Льва, остаётся ждать и только тогда может заказать напиток. Отсутствие заказа остаётся отдельной веткой разговора.

## Авторские напитки

Редактор хранит напитки в проекте рядом с персонажами и диалогами. Каждый напиток имеет стабильный ID, название, описание, посуду, состав по ингредиентам в миллилитрах и допуск сравнения. Это рецепт для распознавания фактически приготовленного напитка, а не новый предмет инвентаря. Допустимые ID посуды и ингредиентов берутся из игрового каталога материалов. Удаление напитка, на который ссылается диалог, блокируется валидатором.

Экспорт: `content/drinks/narrative_drinks.json`, версия 1, массив `drinks`:

```json
{
  "schema_version": 1,
  "drinks": [{
    "id": "vera_stvor_shot",
    "title": "Северный створ без добавок",
    "description": "Рюмка для Веры, если она останется ждать Льва",
    "vessel_id": "test_shot",
    "components_ml": { "test_stvor": 45 },
    "tolerance_ml": 3
  }]
}
```

Сопоставление требует той же посуды, каждого указанного компонента в пределах допуска и отсутствия дополнительных компонентов сверх допуска. Рецепт без компонентов и рецепт, превышающий вместимость посуды, недопустимы. Точные объёмы нужны для распознавания, а не для автоматического приготовления. Пока каталог материалов игры содержит только тестовые ингредиенты и две подаваемые ёмкости, редактор предлагает именно их.

## Пауза и ветки

Узел реплики может завершаться ожиданием подачи. Автор указывает `drink_gate` после текста узла. Поля: `expected_drink_id`, `resume_after` (`served` или `sipped`), `on_expected`, `on_other_drinks` — список пар `drink_id`/`target`, `on_fallback` и `fallback_consumed`. Все цели — ID узлов того же диалога. Порядок исходов: ожидаемый рецепт, явно перечисленные другие рецепты, общий исход. Дубли ID и отсутствующие цели — ошибки. Пока ожидается напиток, ответы не показываются, а продолжение реплики не пропускает паузу.

`served` продолжает разговор сразу после принятой подачи. `sipped` ждёт завершения анимации питья; этот режим нужен для реакции на вкус. Если другой напиток должен быть отвергнут до глотка, автор выбирает `fallback_consumed: false`: гость произносит альтернативную реплику, напиток остаётся у игрока, обслуживания ещё не произошло и можно предложить другой. Для явно перечисленного другого рецепта такой же выбор задаётся в строке исхода. При принятом неподходящем напитке история продолжается по его отдельной ветке после указанного момента.

Редактор показывает ожидание и все исходы на графе, позволяет запустить их в симуляторе и не экспортирует незавершённую схему. В игре результат проверяется по фактическому стакану, не по нажатию авторской кнопки. Подача, расход талона и время подтверждаются один раз только для принятого напитка. Отмена ожидания/разговора не создаёт подачу. Начатое питьё не прерывается переходом к следующему узлу.

Отсутствие напитка не является «неподходящим напитком»: пока ничего не подано, узел ждёт. Если Вера решила уйти без заказа, автор ведёт её в отдельный узел до начала ожидания.

## Совместимость

Старые диалоги без `drink_gate` и проекты без массива `drinks` работают как прежде. Экспорт рецептов подключается только при наличии авторских напитков. Старые `service_event: request_drink` и события памяти обслуживания сохраняют прежний смысл; они не заменяют ожидание конкретного рецепта.
